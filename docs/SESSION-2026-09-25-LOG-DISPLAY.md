## 1. 主题与范围

目标是让 `node scripts/gw.js logs` 的终端输出更便于扫读和定位请求，同时保留查看完整行、获取原始 stdout、筛选请求和持续跟随的方式。不得改写服务端产生日志的 schema，不应为展示优化碰真实密钥、路由、账本或推理请求，也不要求重启常驻网关。

本次实现范围：

- 默认紧凑列布局、日期分组、状态标签和中英文长行折叠；
- 请求 ID、精确路由和异常筛选，以及筛选后取末尾行数；
- 详细、原始输出、宽度指定和持续跟随；
- 控制字符清理、颜色开关、历史 stderr 原有折叠行为；
- CLI 帮助、README、变更记录和回归测试。

本记录中的现状和验证只对应所述本机项目基线（Windows、Node.js 项目、日期 2026-09-25）。不将 CLI 日志格式描述为服务端接口或持久化 schema 的变更。

## 3. 按流程回顾本次实现

### 3.1 确定展示契约

将“日志展示”落实为 CLI 视图功能，不改日志生产方：默认紧凑；`--detail` 查看完整源行形态；`--raw` 仅输出 stdout 原始行；`--id` 和 `--route` 做精确筛选；`-e` 限定失败/警告/重试；`-f` 只跟随 stdout。stderr 是进程级诊断，不参与请求筛选。宽度参数范围为 40..240；紧凑布局在不足 100 列时切换窄屏呈现。

另明确安全与兼容界线：普通视图需要清理终端控制字符；原始模式保留日志源行的字符与时间，不加视图标题或历史 stderr，不能与 `--history` / `--detail` 组合。原始模式不是任意日志文件的字节级副本：只选择 stdout 行，CLI 输出会以行形式打印。持续跟随不扩展为 stderr tail 或全屏仪表盘。

### 3.2 先读实现与测试，再整合

从 `scripts/gw.js` 的日志入口与渲染区、`scripts/test-logging.mjs` 的隔离 CLI 测试开始。使用内置 `Intl.Segmenter`、字符宽度估算与 VT 控制序列清理，不引入运行时依赖。新选项解析、日志解析、过滤、折行、紧凑/详细/原始 renderer 都留在既有 `gw.js` 中，以兼容测试临时副本只复制该文件的做法。

调用关系保持为：读取 stdout 文件末尾最多 2MB → 解析选项并应用筛选 → 选取最后 n 条非空原始行 → 按所选模式渲染；若跟随，则把首次读取的文件偏移、UTF-8 decoder 和未完成行交给跟随循环。对历史 stderr 的 `/health` 判别只在非 raw 视图执行，确认旧记录默认折叠；无法判定当前归属的错误线索不能静默丢弃。

### 3.3 持续跟随的边界修正

第一版跟随仍采用原逻辑：从启动时的当前文件尾开始，直接格式化增量行。检查时发现这不满足新视图契约：初始读取可能留下 UTF-8 字符或未换行半行，且 ID/route/error 过滤与 compact/detail/raw 模式没有沿用。

因此将跟随入口改为接收 options、统一 renderer、快照字节偏移、同一 decoder 和 pending 文本；增量读取每轮不超过 256 KiB，使用实际读取字节数推进偏移。文件被截短时重置 decoder/pending 并从头继续。raw 模式不输出跟随说明横幅；detail 和 raw 都需按请求过滤。新增回归对 UTF-8 多字节字符中途分割、启动时未结束的行、错误筛选、错误 ID/route/status 排除以及文件截短进行验证。

### 3.4 根据失败测试调整兼容断言

第一次运行新紧凑视图后，原 CLI 测试仍把旧格式正文当默认输出合同：默认 `logs 1` 要求输出以 `[` 开头，跟随断言寻找旧正文片段。这些失败反映默认输出形式已改变，而不是应继续让默认紧凑模式伪装成旧布局。将专门验证历史源行形式的断言明确改为 `--detail`，跟随测试改为检查紧凑列渲染后的状态、时间和请求 ID。

测试过程中还暴露窄屏折行按 grapheme 强制切分，可能把数值、单位或错误短语拆在不自然的位置；折行逻辑改为先按空白分词，再对超宽 token 按 grapheme 拆分。标题/筛选说明也要按指定列宽换行，以避免最小宽度下标题自身溢出。

### 3.5 汇总实现、帮助与本地文档

实现收束在 `scripts/gw.js`，离线回归放在 `scripts/test-logging.mjs`。CLI help 和 [README](../README.md) 记录参数、限制和示例；[CHANGELOG](CHANGELOG.md) 保留按日期排序的实施与验证摘要。本文件单独记录会话流程、修正过程和证据界线，供查阅来龙去脉。

## 4. 当前功能速查

| 选项 | 行为 | 边界 |
|---|---|---|
| `logs [n]` | 默认紧凑视图，按日期分组，列出时间、状态、路由、短请求 ID、详情 | 从 stdout 末尾最多 2MB 内选择；n 是匹配的非空源行数，不是请求数或屏幕折行数 |
| `-e` / `--errors` | 只显示异常/警告/重试记录 | 与 ID、route 过滤相交；stderr 是进程级诊断，不按请求过滤 |
| `--id <id>` | 完整 `gw_XXXXXXXX` 或 8 位十六进制 ID 精确筛选 | 支持 `--id=value`；非法或缺值报错 |
| `--route <name>` | 精确匹配路由 | 不做模糊子串匹配；支持 `--route=value` |
| `--detail` | 完整行展示，保留时间戳和正文；旧 UTC 时间转本地显示 | 普通视图会做终端字符清理；不与 raw 同用 |
| `--raw` | 仅输出所选 stdout 源行，不加视图横幅、颜色、时间转换或 stderr | 原文控制字符也保留；请只将可信日志重定向到安全目的地；不等于任意文件的字节级导出 |
| `--width <40..240>` | 指定渲染宽度 | `<100` 列进入窄屏两层布局；字符宽度按 grapheme 与东亚宽度近似估算 |
| `-f` / `--follow` | 在初始末尾视图后继续跟随 stdout 新行 | 共用过滤和渲染；只跟 stdout；Ctrl+C 退出；已打开的跟随命令退出重开以读取新版 CLI |
| `--history` | 显式附加现有 stderr 历史查看行为 | 不自动读取 archive；与 raw 冲突 |

使用示例：

```bash
node scripts/gw.js logs
node scripts/gw.js logs 80 -e
node scripts/gw.js logs --id 5f4c7452
node scripts/gw.js logs --route gemini -f
node scripts/gw.js logs --width 60 --detail
node scripts/gw.js logs --raw
node scripts/gw.js logs --history
```

## 7. 偏差、恢复方式和预防要点

- 多次小范围 `edit` 操作报告成功后，立即读取发现有些替换并未落盘；代码入口调用和新测试也曾仍保留旧版本。以读回的内容和 grep 命中为准，不把“工具报告成功”当作实际变更证据。
- 一次 Node 脚本补丁因 PowerShell/JavaScript 多层字符串中的换行转义破坏语法，在写入前失败。另一批通过 PowerShell here-string 修复测试时，回读发现 JS 字符串里的 `\n` 被变成源代码物理换行；先 `node --check` 发现，再改为 `String.fromCharCode(10)` 并重新检查。这类生成型编辑应避免嵌套转义，采用小的字面补丁并立刻读回/语法检查。
- 初次定向测试出现失败后没有把它当作通过；根据改变后的 CLI 默认合同修正旧测试为显式 `--detail`，再增加适配新行为的独立覆盖。最终以最后一次测试结果为准。
- 故障边界：筛选只对被解析的 stdout 源行生效；进程级 stderr 不属某个请求。终端显示宽度是估算值，并非对所有终端字体/组合字符的绝对测量。raw 模式不清理控制序列，应谨慎输出到交互式终端。
- 没有 Git 仓库，无法以 diff/commit 证明文件变更，也没有提交或推送。并行或旧会话已有的 token 价格配置、usage report 等不相关改动按现有源码保留，不在本次日志展示变更里重归因。
